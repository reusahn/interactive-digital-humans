# Research Session Checkpoint — 2026-09-16 Step 18B1G2

## Purpose

Test whether the remaining Step-17B1 elbow regression mismatch is caused by where the displacement vector subtraction and norm are evaluated, while holding the strict-FP32 CUDA transforms and LBS positions fixed.

Current runtime:

- GPU: `NVIDIA A100-SXM4-40GB`
- PyTorch: `2.11.0+cu128`
- CUDA: `12.8`
- TF32 disabled
- float32 matmul precision `highest`
- elbow frame 2 only
- frozen regression gate unchanged at `1e-5`

## Result

Six mathematically equivalent displacement-evaluation variants were tested:

1. CUDA `torch.linalg.vector_norm`
2. CUDA `torch.norm`
3. CUDA `sqrt(sum(delta^2))`
4. CUDA subtraction then NumPy CPU norm
5. CUDA before/after positions transferred separately, then NumPy subtraction + norm
6. CUDA before/after positions transferred separately, then CPU Torch subtraction + norm

All six produced the same scientific regression outcome:

```text
Seattle learned: PASS, error about +6.60e-06
Seattle K6: PASS, error about +1.51e-06
Parkinglot learned: FAIL, error about +1.1049e-04
Parkinglot K6: PASS, error about +2.40e-06
Jogging learned: PASS, error about -3.93e-06
Jogging K6: PASS, error about +3.70e-07

learned passes: 2/3
K6 passes: 3/3
total: 5/6
EVALUATION-PLACEMENT RECOVERY: False
```

The GPU-native norm variants were bitwise identical to each other. Moving the norm to NumPy or CPU Torch changed fields only at roughly `1e-11` mean absolute scale and did not materially change any aggregate result.

## Additional numerical observation

The archived per-Gaussian arrays summed in float32 reproduce the historical printed Step-17B1 scalar values exactly:

- Seattle learned historical scalar `2.650563955307007`
- Parkinglot learned historical scalar `11.094181060791016`
- Jogging learned historical scalar `1.2263532876968384`

This confirms that the archived arrays and historical printed scalar summaries are internally consistent, with the printed summaries reflecting float32 reduction semantics. The current Parkinglot mismatch is therefore upstream of the final reduction/norm placement.

## Interpretation

Displacement norm implementation and CPU/GPU evaluation placement are ruled out as the source of the remaining blocker. Since strict CUDA FP32 recovers 5/6 conditions and all displacement fields remain spatially almost identical to the archive, the remaining discrepancy is a historical numerical-runtime equivalence issue, most plausibly the CUDA/PyTorch/cuBLAS environment or another lower-level execution-path difference upstream of the norm.

Official HUGS setup documentation provides a concrete reproducibility target: Python 3.8, PyTorch 1.13.1, and CUDA 11.7. This is not proof that the custom Step-17 diagnostic ran under that exact environment, but it is the strongest declared environment target from the released source and should be tested before altering any frozen gate.

No shoulder causal computation was run and no tolerance changed.
